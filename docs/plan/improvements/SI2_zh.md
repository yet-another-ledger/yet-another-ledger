# SI2 · 未交付普通发票的修订
> 🌐 [English](SI2.md) · **中文**

> **状态**：2026-10-26 已确认设计，正在编排实施；作者人工走查尚未进行。SI2 是独立编号的小改进，不是 Milestone，沿用 Milestone 实施计划格式。M15 保持暂停；SI2 不依赖、也不恢复其开发分支。

## 目标与范围

**目标**：普通发票开票后，在尚未交付客户且没有付款时，允许保留状态和单号进行修订，并保留完整修订历史。

**包含**：
- 独立创建的普通发票，以及直接由报价转换、没有预收款的普通发票。
- 日期、参考号、备注、内容块、有序明细及金额输入的修订。
- 后端资格判断、修订计算预览、原子保存和修订历史。
- 保留原始单号、首次开票身份和已留存的 PDF／邮件历史。
- 已交付后提供通往现有更正流程的明确入口。

**不包含 / 顺延**：
- `SENT -> DRAFT`、新生命周期状态，或重新开放已开票单据的删除／取消。
- Advance、Final、Credit Note，以及涉及 receipt-only 预收款、退款、贷项、替代／补偿关系或正式抵扣应用的普通发票修订。
- 交付客户后的原地金额修改。
- 通用数据库审计、恢复历史修订、历史邮件重发或 IMAP 补存。
- 已申报状态跟踪、已申报期间锁定或自动更正税务申报。
- 新的 Terms & Conditions 模板系统或 Dictionary 导航调整。

**T&C 决定**：沿用**内容库 -> 标准内容块 -> Terms & Conditions**。现有功能支持多套命名内容块、可选默认项，以及报价／发票编辑器中的选择。应用时复制文本；之后修改／删除模板不回写已保存文档。第二点请求无需新增实施步骤。

**相关文档 / 已有基础**：[路线图](../roadmap_zh.md)、[M5](../milestones/M5_zh.md) 定价与发票 CRUD、[M6](../milestones/M6_zh.md) 内容快照、[M7.5](../milestones/M7.5_zh.md) 舍入、[M9](../milestones/M9_zh.md) PDF／邮件、[M12](../milestones/M12_zh.md) 单据链与贷项依据、[M13](../milestones/M13_zh.md) 历史 PDF 留存，以及 [SI1](SI1_zh.md) 明细排序和发件副本行为。

## 冻结的产品与架构决策

- [x] **D1 · 保留已开票身份**：修订保持 `SENT`、发票号／序列号／客户序列号、首次 `issued_at`、首次开票人，以及冻结的公司／客户身份快照。不再次开票。
- [x] **D2 · 交付边界**：存在任何成功的发票邮件日志时禁止修订；没有成功日志时，保存仍须明确确认尚未通过其他渠道交付。下载 PDF 本身不代表交付。SI2 不增加外部交付的自动检测。
- [x] **D3 · 没有有效付款**：查询实际未删除的 Payment 记录，不能只看 `paid_status` 或金额缓存。部分收款也禁止修订。
- [x] **D4 · 没有依赖的更正／结算链**：已有贷项草稿或已开贷项、退款、替代／补偿关系、Advance／Final 应用或 receipt-only 付款来源时禁止修订。不通过删除或破坏依赖记录来满足修订资格。
- [x] **D5 · 客户与币种固定**：可改日期、参考号、备注、内容块、明细、数量、价格、折扣及税务选择；不能通过修订改变客户、币种、编号、生命周期或来源关系。
- [x] **D6 · 不隐式刷新主数据**：只改日期／文字时保留全部金额及税务快照。金额变化使用现有后端定价核心；未改变的税务选择沿用冻结快照，不随之后的字典修改漂移；目录价格变化不能覆盖输入单价。
- [x] **D7 · 当前贷项依据一致**：明细修订同步维护日后开贷项使用的当前源依据。不能调用普通草稿更新后，假定再次开票会修复快照：现有开票初始化遇到已有身份快照时会提前返回。
- [x] **D8 · 同事务审计**：每次实际修订记录操作人、时间、必填原因、未交付确认及完整前后业务快照，与修改同事务提交。失败不留下半次修订。
- [x] **D9 · 保留历史输出**：不回写／删除现有 PDF、邮件日志或附件关联。实时预览和后续下载／发送按 M12／M13 的呈现指纹规则使用当前内容；相同呈现仍可复用已有原始字节。
- [x] **D10 · 不自动发邮件**：计算、保存修订及查看历史均不发送邮件，也不追加发件副本。
- [x] **D11 · 报表只计当前票一次**：更新原发票，修订不是额外收入／VAT 事件。改日期可能改变当前报表所属期间；跨期时展示前后期间，不声称知道期间是否已申报。
- [x] **D12 · 交付后更正**：减价使用部分 Credit，加价另开注明原票的普通发票，整票重做使用全额 Credit 加替代发票。复用现有流程，不新增补票业务模型。
- [x] **D13 · 没有删除逃生口**：已开票且有编号的发票继续不可删除；修订资格不授予新的取消、删除或状态流转权限。

## 契约（先定义）

### 修订变更与预览

定义使用字段白名单、拒绝额外字段的 `InvoiceRevisionChanges`：

- 省略字段保留当前值；显式 `null` 只可清空允许为空的字段。
- 头部字段：`invoice_date`、`due_date`、`supply_or_advance_date`、`reference_number`、`notes`、`warranty_text`、`terms_text`、`bank_text`、`payment_terms_text`。
- 定价字段：`tax_mode`、`amounts_include_vat`、`vat_treatment_id`、`document_vat_rate_id`、整单 `discount` 和 `lines`。
- 传入 `lines` 时表示完整的目标顺序数组，至少一行。每行使用已有原始明细输入及可选 `line_id`：保留行携带原行标识，新行省略，未出现在数组中的原行被删除。
- 拒绝重复、未知或其他发票的行 ID。拒绝客户、币种、编号、状态、来源及客户端计算金额等受保护字段，不接受任意 ORM／读取模型载荷。

`POST /api/v1/invoices/{invoice_id}/revisions/calculate`：

- 请求 `InvoiceRevisionCalculateRequest { expected_updated_at, changes }`。
- 响应 `200 InvoiceCalculationRead`，复用现有计算结果结构及请求数组顺序。
- 一致性读取原票、验证请求版本、合并变更并计算；不持久化，不创建审计／事件／PDF，不分配编号、不发邮件。
- 预览不保留修订资格；保存获取锁后重新验证所有条件。

### 保存与历史

`POST /api/v1/invoices/{invoice_id}/revisions`：

- 请求 `InvoiceRevisionCreate { expected_updated_at, changes, reason, confirm_not_delivered }`。
- `reason` 不能只有空白；`confirm_not_delivered` 必须显式为 `true`。
- 响应 `200 InvoiceRead`，包含后端权威的当前修订资格。
- 持锁后比较 `expected_updated_at` 与持久化版本；过期请求返回 `409`，不应用其中任何部分。
- 其他条件均合法但没有实际变更时返回当前发票，不新增修订／事件，也不改变 `updated_at`。

`GET /api/v1/invoices/{invoice_id}/revisions`：

- 沿用现有列表约定，返回分页 `InvoiceRevisionListRead { items, total }`，按数据库生成的修订顺序从新到旧排列。
- 每条 `InvoiceRevisionRead` 暴露标识、稳定顺序、操作人、时间、原因、未交付确认及完整且有类型的前后业务快照。
- 不提供修改／删除／恢复修订的接口。

发票详情增加 `revision_eligibility { available, reason_code }`。读取投影与持锁命令复用同一个后端资格判断，不在发票列表中引入逐行资格查询。

### 权限、错误与兼容

- 使用现有 MFA owner 权限及公司 RLS。非 owner 返回 `403`；不存在／跨公司发票返回 `404`，不披露历史。
- 状态、有效付款、交付、关联链及版本冲突返回带稳定原因码的 `409`；非法字段／日期／金额／引用／原因／确认返回 `422`。
- 普通草稿 PUT、计算及状态接口保持兼容，不能允许绕过审计的 `SENT` 修改。
- 契约变化时重新生成并提交 OpenAPI TypeScript 类型。路由保持薄层；资格、合并、定价及持久化位于 `services/`。

## 数据模型 / 迁移

### 新增修订表

增加 `invoice_revision`：

- UUID `id`、`company_id`、`invoice_id`、可空 `actor_user_id`，以及带时区 `created_at`。
- 数据库生成的唯一稳定顺序值，禁止通过 `max+1` 分配。
- 使用 `text` 存储非空 `reason`，并保存明确的未交付确认。
- `before_snapshot` 与 `after_snapshot` JSONB，由专用、带版本的 Pydantic 业务快照 schema 校验；包含头部／原始字段、有序明细、税务快照、计算金额及对应贷项依据。
- Decimal 序列化为字符串，日期为 ISO 值；不保存凭据、原始请求外壳、ORM 状态或任意上下文。
- 公司 RLS、发票／公司所有权校验及运行时只追加权限；遵循现有 FK／ORM 归属约定，不手写级联删除。

### 现有事件流水

- 增加 `DocumentChainEventType.INVOICE_REVISED`。
- 定义引用修订记录 ID 的封闭安全事件元数据；完整文字与前后内容放在修订表，不放进通用事件元数据。
- 修订记录、当前发票变更及事件同事务持久化。

### 升级与历史兼容

- 在当前 `main` 线性头上增加迁移，与暂停的 M15 工作分开。
- 不修改／重算历史发票、付款、编号、PDF、邮件或报表数据。
- 不补造早期修订；第一次新修订以当时持久化状态作为修改前快照。
- 测试空库、接近生产的数据升级，以及隔离环境中的降级／再升级，覆盖运行时角色及公司隔离。

### Step 2 · 保留税务快照的修订预览

- **状态**：自动化实施、完整本地门禁及独立盲审已完成（2026-10-26）；作者人工走查待进行。
- **目标**：修订预览与后续保存使用同一套合并和计算规则。
- **契约**：实现 `InvoiceRevisionChanges`、原有行标识及 `/revisions/calculate`，重新生成类型。
- **后端**：一致性读取原票并合并白名单变更，识别实际变化：只改头部／文字时保留金额，否则调用现有定价核心。
- **税务解析**：保留行未改变税率选择时使用该行冻结税率；新增行或显式改选时读取所选有效字典记录。treatment 与整单税率遵循同类快照保留规则。支持同一 rate ID 在不同行拥有不同冻结百分比，不能用单个当前字典值覆盖。
- **定价**：不从目录刷新单价；保持 M7.5 舍入和 SI1 排序行为。所需快照输入适配留在定价 service 内，不增加第二套算术引擎。
- **前端**：仅生成类型，Step 4 再开放编辑器入口。
- **迁移**：无。
- **测试**：日期／文字修改保留金额；增删改行／排序；数量／价格／折扣／混合 VAT／含税输入；字典变化与不变快照；主动税务变更；非法／重复行 ID；过期版本；预览不改变任何业务表。
- **盲审点**：不误用普通草稿预览而静默刷新 VAT；新旧快照可并存；省略与清空语义不同；金额计算只在后端 service。
- **DoD**：路线图 §5；本地写 `review-notes/SI2-step2-impl.md`。

### Step 3 · 原子保存修订与并发保护

- **状态**：自动化实施、完整本地门禁及独立盲审已完成（2026-10-26）；作者人工走查待进行。
- **目标**：提交一次完整审计的修订，保证金额、应收额和以后贷项依据一致。
- **契约**：实现 `POST /revisions`，包含原因、未交付确认及版本校验，重新生成类型。
- **后端**：遵循现有 Quote -> Invoice 锁顺序，再读取发票／版本、付款、成功邮件及依赖单据，复用 Step 2 的合并／定价实现。
- **持久化**：日期／头部文字变化不重建金额或明细；明细变化通过现有 FK／ORM 归属维护相关行、税务快照及当前贷项依据。更新应收／结算缓存，保存前后快照并追加修订事件，全部同事务完成。
- **身份**：保留 `SENT`、所有已分配编号、首次开票身份／时间／人及来源；不重跑开票初始化、不替换身份快照。
- **并发**：修订、付款、贷项创建及发邮件使用兼容的父记录锁；禁止在邮件渲染至发送结果提交之间插入修订，客户附件、邮件正文与日志必须对应同一版本。重新检查，不信任无锁发现读取。
- **失败流程**：旧版本／重复请求返回 `409`；合法无变化请求不增加历史；任何失败回滚全部修订状态。普通 PUT 继续拒绝 `SENT` 编辑；不自动发邮件或重试。
- **前端**：仅生成类型，在 Step 4 完成工作流前继续隐藏修订入口。
- **迁移**：无，使用 Step 1 存储。
- **测试**：前后值；金额／应收／依据守恒；修订后付款和贷项；重复提交；并发修订／付款／SMTP／贷项创建；保存中途注入失败；历史不可改写；其他接口不能绕过审计。
- **盲审点**：没有检查／写入竞态、过期 ORM 投影、临时 DRAFT、开票快照刷新、孤立／过期依据或手写级联清理。
- **DoD**：路线图 §5；本地写 `review-notes/SI2-step3-impl.md`。

### Step 4 · 修订编辑器与历史工作流

- **状态**：未开始，依赖 Steps 1–3。
- **目标**：在现有发票工作区完成修订，并与交付后的更正清晰区分。
- **契约**：消费生成的资格、预览、保存及历史类型，Vue 不增加金额计算。
- **后端**：复用已完成的资格、计算、保存及历史 service，不增加额外业务接口或计算算法。
- **前端**：后端资格允许时展示「修订」，复用编辑器和明细排序，锁定客户、币种和编号；使用修订预览，忽略被后续请求取代的计算响应。
- **确认**：展示主要变更，要求原因和明确的未交付确认；改日期跨报表期间时展示前后期间，不推断申报情况。
- **保存／取消**：阻止重复提交；失败／冲突时保留本地输入，提示重新读取当前数据，不自动覆盖／重试；取消／导航复用现有未保存修改保护。
- **历史**：操作人、时间、原因、字段前后值和有序明细以只读转义文本显示，不执行 HTML。
- **已交付单据**：解释边界并提供现有 Credit／替代流程入口；加价沿用普通新建发票，通过已有参考号／备注注明原票，不新增补票模型。
- **T&C**：修订表单复用内容块选择；应用仍为文本复制，已保存文档不追踪模板后续变化。不增加 Dictionary 页面或另一份模板存储。
- **迁移**：无。
