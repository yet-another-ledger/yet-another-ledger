# M19 · Purchase Receipt AI Recognition and VAT Treatment Prefill

> 🌐 **English** · [中文](M19_zh.md)

> ⬜ **Design agreed on 2026-11-10, implementation pending.** This milestone follows the accepted M18 baseline on `main`. The [roadmap](../roadmap.md) tracks implementation progress. The current released version is v0.14.0.

## Goal and scope

Include the purchase VAT treatment in the existing AI receipt extraction, reducing accidental manual selection of the wrong treatment. Prefill the receipt-inbox review form and offer the same suggestion in the Expense attachment extraction workflow. The owner reviews the editable form and explicitly confirms or saves it.

The field is the existing `ExpenseInput.vat_treatment_id`. Expense category, VAT rate and VAT deductibility have separate meanings. The first version recognizes three existing purchase treatments, defined in D1. Non-EU purchases, special cases and insufficient evidence require manual selection.

Coverage includes the M14 receipt inbox and the M8 Expense editor. Receipts submitted through M15 MCP use the same inbox extraction and web review. External sales extraction, VAT dictionaries and reporting mappings, deduction policy, recurring-expense generation and historical bookings are outside this feature's implementation scope. There is no automatic posting, batch reclassification or new MCP tool/scope.

## Frozen product and architecture decisions

### D1 · Classify from document evidence

| Existing treatment | Required evidence in the prompt | Expected dictionary effect |
| --- | --- | --- |
| `NL_DOMESTIC_PURCH` | The document clearly charges Dutch VAT and supports a Dutch purchase, such as a local receipt from a Dutch merchant. | `APPLY_RATE` |
| `EU_B2B_REVERSE_PURCH` | Evidence identifies a supplier in another EU member state and a Dutch business purchaser, with an explicit buyer-side reverse-charge statement or an identifiable intra-community supply delivered to the Netherlands. The supplier has not charged VAT. | `ZERO_REVERSE` |
| `EU_B2C_PURCH` | The document clearly charges the local VAT of another EU member state and provides evidence consistent with the application's existing foreign-VAT purchase treatment. | `APPLY_RATE` |

These codes bound the recognition feature. Resolve them to the company's existing dictionary records at runtime. Labels, IDs, rates and filing mappings remain data-driven. The existing `EU_B2C_PURCH` label is used for display, and the suggestion alone does not establish the purchaser's legal status.

Consider the actual invoicing entity, supplier and buyer roles, the country whose VAT is charged, tax wording and delivery information. Currency, document language, brand headquarters, a tax-rate number or a lone `0%` cannot establish the treatment. Domestic reverse charge, non-EU purchases, apparent special tax regimes, conflicting evidence, mixed tax treatments or unrelated transactions in one group yield no treatment suggestion. Other extractable fields may still be returned. EU transactions can require self-assessment even when the supplier charges no VAT, and foreign VAT has separate deduction rules. [Tax Administration EU purchase guidance](https://www.belastingdienst.nl/wps/wcm/connect/bldcontentnl/belastingdienst/zakelijk/btw/zakendoen_met_het_buitenland/goederen_en_diensten_afnemen_uit_andere_eu_landen/btw_berekenen_over_goederen_en_diensten/), [cross-border input VAT guidance](https://www.belastingdienst.nl/wps/wcm/connect/bldcontentnl/belastingdienst/zakelijk/btw/btw_aftrekken/welke_btw_is_aftrekbaar/btw_aftrekken_als_u_zakendoet_met_het_buitenland).

### D2 · Extend the existing prompt and validate one suggestion

Use one model call per extraction through the shared purchase core. Keep the existing extraction instructions, additive custom `receipt_prompt`, date context and EN/ZH explanatory-language behavior. Append a fixed purchase-classification instruction after the custom instructions and runtime context, immediately before the final JSON output contract. The contract remains the final block.

The classification block describes D1, includes one positive example for each supported treatment and negative examples for lone zero VAT, conflicting countries, domestic reverse charge and non-EU documents. It requires treating document content as untrusted evidence and ignoring instructions printed in documents. Custom instructions cannot expand the accepted treatment codes or the output schema. Backend validation remains necessary even when the prompt requests compliant output.

The model may return `vat_treatment_suggestion` with `code` and `reason`. The reason is one short plain-text statement of visible evidence, such as “German supplier invoices a Dutch business and states reverse charge”. It follows the requested EN/ZH language, with a maximum of 240 characters. The prompt instructs the model to omit full VAT IDs, addresses and other unnecessary identifiers from the reason. Codes remain language-independent.

The service requires an object with a supported string code and a nonempty string reason after trimming. Reject overlong reasons, malformed shapes and clearly contradictory combinations, including `EU_B2B_REVERSE_PURCH` with a positive parsed supplier VAT amount. Discard the treatment suggestion alone when it is invalid, preserving other valid extracted fields. Missing evidence produces a null suggestion. The existing overall `confidence` field remains advisory and is not a new automatic-selection threshold.

Resolve the code through the existing company-scoped VAT service. A match must belong to the current company, be active, have `side=PURCHASE` and have the effect specified in D1. A missing, disabled or semantically changed record yields no suggestion. The model never supplies the accepted UUID. Reuse established authorization and company isolation rather than adding scattered company filters or a new classification table.

Persist only the validated suggestion in the inbox's existing JSONB. Render its reason through escaped text interpolation. Continue excluding raw provider replies, credentials, encoded originals and storage paths from public suggestions and logs.

### D3 · Protect human choices and apply current suggestions

| Current treatment field | Behavior on a new valid suggestion |
| --- | --- |
| Empty and untouched | Automatically fill it and mark its source as AI. |
| Filled by the preceding AI suggestion | Replace it with the new suggestion. |
| Manually selected or manually cleared | Preserve it and show a different available suggestion with an **Apply suggestion** action. |
| Loaded from a saved Expense | Preserve it and offer **Apply suggestion** when the suggestion differs. |
| Explicitly applied with **Apply suggestion** | Treat it as a human choice for subsequent extraction. |

Show the dictionary label, AI origin and evidence beside the field. A matching human value needs no redundant apply action. If the latest completed extraction fails or has no usable treatment, remove the old suggestion and clear only the treatment value owned by that suggestion. Preserve human values. Invalidate the old suggestion when the file group changes. During a retry on the same group, the previous AI-owned value may remain while extraction is running, but the running state must be visible and the old apply action unavailable.

Before application, check the suggested ID and code against the page's loaded purchase dictionary, including active state and the expected effect. If the dictionary arrives after extraction, retry application after loading while still honoring human edits. An unavailable suggestion leaves manual selection available. Human protection is per form session, consistent with the existing unsaved inbox form.

Only results for the current item, file group and latest extraction may update suggestion state. Guard route changes, overlapping detail/mutation responses, confirmation and saves so late results cannot apply to another item or restore an outdated proposal. Continue using the inbox service's file-revision and extraction-generation checks. Saving an Expense makes its current treatment a saved human value.

The Expense editor allows attachment upload only after the Expense exists. This entry therefore usually presents an explicit apply action for the saved treatment. Applying a suggestion changes only the editable form until the owner saves it. Inbox confirmation continues to create one Expense through the existing atomic confirmation workflow.

### D4 · Keep receipt VAT separate from the reverse-charge reporting rate

The existing Expense record stores receipt net/VAT amounts and a VAT rate. For EU B2B reverse charge, the reporting service uses that rate to calculate self-assessed VAT. Supplier zero VAT does not establish a zero reporting rate. The Tax Administration requires determining the applicable Dutch rate for the acquired goods or services. [Tax Administration EU purchase calculation guidance](https://www.belastingdienst.nl/wps/wcm/connect/bldcontentnl/belastingdienst/zakelijk/btw/zakendoen_met_het_buitenland/goederen_en_diensten_afnemen_uit_andere_eu_landen/btw_berekenen_over_goederen_en_diensten/).

For a validated EU B2B reverse-charge classification, retain the extracted receipt `vat_amount` and return no `vat_rate_percent` prefill from that extraction. The prompt requests manual review of the nominal rate, and the service enforces this separation. A missing receipt VAT amount stays missing. Suppress the rate prefill even if the recognized reverse-charge code cannot resolve to an eligible dictionary entry.

In both purchase forms, selecting a reverse-charge treatment prevents AI from applying a receipt rate to the nominal-rate field. A rate previously filled by the superseded AI suggestion is cleared when an AI treatment change requires manual nominal-rate selection. Existing human or saved rates are preserved for review. Show a localized instruction to verify or select the applicable nominal rate. Other recognized treatments continue to use the existing rate dictionary and extraction behavior.

While a reverse-charge treatment is selected, the generic net-times-rate preview must not overwrite receipt VAT. Invalidate pending timers and responses when treatment or relevant input changes so an earlier ordinary-VAT request cannot overwrite it either. Keep receipt amounts editable and clear an invalidated gross preview until a valid existing backend result is available. All monetary calculations continue in backend services. M19 does not introduce a new reporting calculation or infer deductibility from the treatment suggestion.

## Contract and data compatibility

| Surface | Additive change |
| --- | --- |
| Model JSON | Optional `vat_treatment_suggestion` object with `code` and `reason`, or null. |
| `ExpenseAIPrefill` | Optional, nullable `suggested_vat_treatment`, default null, containing `id` (UUID), `code` (string) and `reason` (string, 1–240 trimmed characters). |
| `POST /api/v1/expenses/ai-extract` | Returns the extended prefill. Existing request and error handling remain applicable. |
| `ReceiptInboxRead.ai_suggestion` | Uses the same extended prefill and existing JSONB storage. A valid treatment-only suggestion counts as presentable and may produce `READY`. |
| Frontend generated API types | Regenerate committed `schema.d.ts` when Step 1 adds the response contract. |

The model field carries a proposed code. The public response field carries a service-resolved dictionary reference. Unknown model fields, including supplied IDs, never become trusted references. Schemas validate shapes, while services perform classification checks and dictionary resolution.

Existing stored suggestions without the new field read as null. There is no database migration, historical backfill or automatic re-extraction. Existing `ExpenseInput` confirmation/save payloads remain the booking contract. AI failure follows the existing unavailable/failed states and manual-review fallback. A valid type-only result is `READY` with other missing fields still requiring review. M15 transport/status contracts and M16 external-sales extraction retain their respective scopes.

7. Open an existing Expense, upload an attachment and request extraction. Verify the saved treatment is retained, apply a different suggestion, inspect all fields and save. Verify persistence after reopening.
8. Open an older inbox item whose stored suggestion lacks the new field. Verify normal review and manual treatment selection. Check the AI-disabled/failure path with isolated configuration and confirm manual completion remains possible.
