# M18 · Agent Mileage Intake through MCP

> 🌐 **English** · [中文](M18_zh.md)

> **Design agreed (2026-11-10)** Four atomic task cards are ready for implementation. Delivery progress is tracked in the [roadmap](../roadmap.md). The tools and permission below describe the planned capability.

## Goal and scope

Let an authorized Agent collect a complete trip, obtain a JAI calculation preview, ask the user to confirm it, and atomically create the mileage trip and its linked Expense. Support any client compatible with the existing JAI MCP connection and authentication boundary.

- Included are active transport choices, complete mileage previews, confirmed single-trip creation, stable retries, owner-managed permission, and client-neutral workflow documentation.
- The Agent can use its own available web search or mapping tools to suggest a route distance. The user confirms the kilometres used for accounting.
- Historical mileage search/detail tools, mileage editing/deletion, configuration management, draft/review queues, bulk creation and JAI-hosted map integration remain follow-on work. Existing Expense reads retain their SI4 scope.
- Foundations are [M11 mileage](M11.md), [M15 Agent access and idempotency](M15.md), and [SI4 expense reads](../improvements/SI4.md). Shared in-app address search/routing remains the separate roadmap §4.ab backlog.

## Frozen product and architecture decisions

### D1 · Client-neutral responsibilities

The Agent interprets natural language, resolves missing or ambiguous facts, obtains route suggestions when possible, and asks for confirmation. JAI validates structured inputs, authorization and company ownership, then uses existing mileage services for rates, Decimal calculations and Expense projection. All displayed financial figures come from JAI.

Search or map results must identify the endpoints, travel mode, suggested distance and source. The Agent asks for kilometres when reliable route evidence is unavailable. The user can override a suggestion. Route evidence is presented in the conversation, with optional user-requested context in the existing note field. This milestone adds no map-provider credentials, coordinates, provider response storage or external HTTP requests to JAI.

### D2 · Complete trip and explicit confirmation

Reuse `MileageExpenseWrite` semantics. Require a definite trip date and positive one-way kilometres. An omitted transport ID uses the company default, which must be shown in the preview. Show single/return trip explicitly even though the existing schema defaults `round_trip` to false. Origin, destination, purpose and note remain optional text.

Read enabled transport types before choosing a user-named type. Ask about ambiguous names. A trip uses one enabled type and the existing private-transport mileage workflow. Unequal outbound and return distances are recorded as separately previewed and confirmed one-way trips. Each operation creates one trip.

The Agent presents all supplied trip fields, the resolved transport and category, total kilometres, effective rate/date, amount and currency, then waits for the user's confirmation. Creation produces a formal mileage Expense included in existing reports. The MCP description and owner permission label must make that effect clear.

### D3 · Preview bound to the proposed booking

JAI returns a versioned HMAC `preview_token`, using the existing signing-secret facility and canonical typed serialization. Bind the company, Agent token ID, request ID, optional source, complete normalized trip input, and the resolved facts used for the trip and Expense snapshots. Those facts include transport identity/name, rate identity/scope/effective date/value, total distance, amount, currency, category and VAT projection facts.

Use an M18-specific signing domain/version. Compare signatures in constant time. The default is content validity without a separate time expiry. Signing-secret rotation invalidates outstanding previews. The token establishes which calculation JAI supplied. The Agent is responsible for obtaining human confirmation.

Preview runs full creation validation, including category and VAT prerequisites. At creation, reacquire the existing company mileage lock, resolve the current facts and verify the token before any business insertion. Persist the same resolved values that were verified. Changed inputs or changed relevant resolved facts require another preview and confirmation. Unrelated configuration edits do not invalidate an otherwise identical booking.

### D4 · Current settings and atomic transactions

Extract a flush-only transaction primitive from the existing mileage creation service. The owner API wrapper retains responsibility for its commit/rollback. MCP uses the primitive inside `run_agent_mutation`, committing trip, linked Expense and operation snapshot together.

Use the existing company mileage advisory lock before dependent lookups in both preview and creation. Keep the existing lock order for rate/type/default writers. Add an opt-in cache bypass to typed settings reads and use it for the mileage defaults used by options, preview and creation. A bypass reads the database and neither reads nor populates the process cache, while retaining existing type validation and fallback rules.

Reuse existing pricing and projection logic. The validated pricing object is the source of the inserted snapshots, avoiding a second calculation between signature verification and insertion. The creator is the authenticated token's owner. Preserve existing Decimal precision, currency rounding, zero-VAT projection and P/L behavior.

### D5 · Stable attempts and exact replay

Generate one stable UUID before preview and retain it through confirmation and creation. Retain the same optional source metadata throughout that attempt. In Telegram integrations, derive it from the initiating trusted event with the `create_mileage_expense` operation name. Generic clients can generate a UUID and omit source.

An identical network retry uses the original ID, source, body and preview token. A new trip, changed input or renewed confirmation attempt after a failed/stale creation uses a new ID. A successfully submitted operation with a lost response must be retried unchanged before starting another attempt.

Use the existing company/token/request uniqueness and normalized argument digest, including the preview token. After authenticating and authorizing, check existing operations before validating a preview against live business settings. Successful replay returns the original response even if settings changed or the target was edited/deleted. Revoked credentials cannot replay. Existing M15 failed-operation persistence applies, so corrected attempts require a new request ID.

### D6 · Permission, isolation and retained results

A single explicit `mileage:create` permission grants the three intake tools. It includes the limited option/preview reads necessary to create mileage. Existing tokens receive it only through an owner-created replacement token. Every call checks permission and revocation.

Use the authenticated company context with the non-superuser runtime role. Agent token/operation tables retain their RLS policies. Existing mileage, settings and Expense access reuses their current service ownership boundary under roadmap §3.3 and M15/SI4. Add no scattered company predicates in MCP handlers. Tests must exercise actual cross-company IDs through the runtime role and must describe the isolation mechanism accurately.

Add an allowlisted mileage result snapshot and matching target-ID validation to Agent operations. The snapshot retains typed trip fields, amounts and the original web link under M15's replay rules, including after target deletion. Retain existing credential/file-content screening. The preview token participates in the request digest and is excluded from response snapshots and logs.

## Contract

All tools use the existing `/api/v1/mcp` endpoint. Root and nested mileage inputs reject unknown fields while reusing existing mileage field types and validation. Distances support the existing Decimal representation. Callers supply raw trip inputs, and JAI supplies rates and financial values.

| Tool | Input | Output | Permission |
| --- | --- | --- | --- |
| `get_mileage_options` | Empty typed object | `default_transport_type_id`, `transport_types[{id,name}]` containing active types | `mileage:create` |
| `preview_mileage_expense` | `request_id`, optional `source`, `mileage` with the complete `MileageExpenseWrite` fields | `request_id`, normalized `mileage`, resolved `transport_type{id,name}`, `expense_category{id,name}`, `calculation` using `MileageCalculationRead`, `preview_token` | `mileage:create` |
| `create_mileage_expense` | The same `request_id`, `source`, `mileage`, plus `preview_token` | Existing `AgentWriteResult` envelope plus `mileage` using `MileageExpenseRead` | `mileage:create` |

The normalized preview input retains a null/omitted transport choice as null, while `transport_type` identifies its resolved default. This preserves detection of a default changing between preview and creation. Source is validated through the existing `AgentSource` contract. UUIDs and dates retain existing API serialization.

Creation returns `operation_id`, `status=created|replayed`, `target_id` equal to the trip ID, and the `BASE_URL`-derived `/expenses/mileage/{trip_id}/edit` web link. The mileage response includes its linked Expense ID. The persisted replay payload consists of the typed mileage response and web link, with the usual envelope reconstructed by Agent operations. Use target type `mileage`.

Options and previews create no trip, Expense or Agent operation row. Normal token last-used tracking still applies. The shipped surface is currently 18 tools/nine scopes. After Step 2 the intended surface is 20 tools/ten scopes, and after Step 3 it is 21 tools/ten scopes.

### Error behavior

- Reuse `MCP_UNAUTHENTICATED`, `MCP_INSUFFICIENT_SCOPE`, `MCP_VALIDATION_FAILED`, `MCP_TARGET_NOT_FOUND` and `MCP_REQUEST_ID_CONFLICT`, plus the existing Host/Origin boundary errors.
- Missing and foreign explicit transport IDs both return `MCP_TARGET_NOT_FOUND`. Inactive transport or missing/invalid default, rate, category or VAT configuration returns `MCP_MILEAGE_CONFIGURATION_INVALID`.
- A missing or structurally malformed preview token fails input validation. A well-formed token that does not match the current attempt/resolved facts returns `MCP_MILEAGE_PREVIEW_STALE`. The Agent requests a fresh preview and confirmation.
- Existing request-ID conflicts are resolved by the operation wrapper before live preview validation. Configuration/lookup errors encountered while resolving a new attempt retain the codes above.
- Register the new errors in the MCP safe-error allowlist and typed error vocabulary. Never return raw validation input, credentials or database exceptions.

## Data models and migrations

- Reuse mileage trip, Expense and Agent operation tables. Extend the typed operation snapshot allowlist for `mileage` and its trip ID.
- Add an Alembic migration after the current `0057` head to extend the token-scope CHECK constraint with `mileage:create`. Preserve released migrations and existing token/operation rows.
- Follow SI4 downgrade protection. Any stored token containing `mileage:create`, including a revoked token, blocks the narrower constraint transactionally. Operators restore a matching pre-upgrade backup when this guard prevents rollback.
- Add the typed scope to the owner token API and EN/ZH Agent access UI. Regenerate committed OpenAPI TypeScript types when the contract changes. Document the new scope as permission to create formal mileage expenses.

## Atomic task cards

Dependencies are **1 → 2 → 3 → 4**. Every card follows roadmap §5 DoD. Related tests must cover happy paths and corner cases. Use isolated temporary resources and clean them up. Implementation briefs remain local and ignored.

### Step 1 · Transaction-compatible mileage creation

- **Goal / contract**　Deliver a transaction primitive with the existing owner request/response behavior.
- **Backend**　Extract flush-only creation. Keep owner commit/rollback in its wrapper and reuse the same pricing, snapshot and Expense projection. Add opt-in settings cache bypass and thread it through mileage default resolution for later intake use.
- **Frontend / migration**　None required for this internal service step.
- **Tests**　Existing owner create/get/calculation and report regressions. Outer rollback removes both trip and Expense, exceptions leave no partial record, and the primitive never commits. Verify fresh defaults with a warmed stale process cache, typed validation and fallback, including cache bypass avoiding uncommitted-value caching.
- **Blind-review points**　One money calculation path, clear transaction ownership, usable response before commit, original owner API behavior, and narrowly scoped cache changes.
- **DoD / report**　Repository gates and `review-notes/M18-step1-impl.md` with automated evidence and owner API walkthrough.

### Step 2 · Permission, options and trusted preview

- **Goal / contract**　Deliver `mileage:create`, `get_mileage_options` and `preview_mileage_expense` with the schemas and errors above.
- **Backend / migration**　Implement the additive scope migration, per-call authorization, typed tools, full creation prerequisites, canonical signing and company-locked preview using fresh defaults. Expose only working tools at this step.
- **Frontend**　Add the localized permission label/description and regenerate TS types. The label explains formal Expense creation enabled by this capability once the create tool lands.
- **Tests**　Default and explicit transport, disabled/missing/foreign types, empty/invalid options, one-way/return trips, Decimal bounds and overflow, no applicable rate, invalid category/VAT setup, forbidden extra fields, authorization/revocation, and zero business/operation inserts. Check canonical-equivalent values, all signed input/resolved fields, cross-token/company signatures, migration compatibility and downgrade protection. Cover permission UI and generated types.
- **Blind-review points**　A complete confirmable preview, real creation prerequisites, current settings across workers, accurate permission mapping, safe errors, and old-token compatibility.
- **DoD / report**　Both tools work through MCP, gates pass, and `review-notes/M18-step2-impl.md` records protocol evidence and permission/preview walkthrough.

### Step 3 · Confirmed creation and exact replay

- **Goal / contract**　Deliver `create_mileage_expense`, the mileage result snapshot and stable failure/replay behavior.
- **Backend**　Integrate `run_agent_mutation`, owner attribution, locked preview verification and Step 1 creation. Persist the verified pricing object. Extend target type, snapshot allowlist, ID matching and safe errors. Generate the existing mileage editor link from `BASE_URL`.
- **Frontend / migration**　Use the existing mileage editor and list. Regenerate types if implementation exposes additional OpenAPI contract changes.
- **Tests**　Successful creation/projection, tampered preview, changed input/default/rate/category, cross-company/token attempts, insufficient scope, concurrent identical requests, conflicting payloads, response loss after commit, rollback at each write boundary, and revocation races. Replay after settings changes, target edits/deletion and signing-key rotation returns the stored success. Failed/stale attempts require a new ID. Existing owner creation, Expense reads, P/L and zero-VAT behavior remain covered.
- **Blind-review points**　New writes require a matching preview, verified and persisted facts agree, operations and business rows commit together, replay cannot create replacement targets, and result screening/tenant checks hold.
- **DoD / report**　The three tools form a complete workflow, gates pass, and `review-notes/M18-step3-impl.md` records normal and retry walkthroughs.

### Step 4 · Client-neutral workflow and milestone acceptance

- **Goal / contract**　Document the complete workflow and validate it across the MCP boundary with isolated data.
- **Documentation**　Add a bilingual client-neutral guide at `docs/plan/milestones/M18-agent-workflow.md` and its mirror. Cover transport selection, route evidence/manual fallback, full previews, explicit confirmation, stable IDs/source across turns, response-loss retries, renewed stale attempts and exact result links. Link it from README and the current full Hermes workflow. Update that workflow's allowlist and mileage-specific instructions, including its existing blanket Expense-posting prohibition. Preserve the scopes of other role-specific profiles and historical M15 acceptance evidence.
- **Protocol acceptance**　Use a dedicated PostgreSQL database, temporary loopback TCP MCP server and two synthetic companies under the runtime role. Exercise discovery, options, preview, create, replay, denied scope, revocation and cross-company IDs. Controlled route evidence covers valid suggestions, ambiguity and failed-query fallback. Actual web/map lookup is exercised when available in the chosen client's deployment walkthrough.
- **Gates**　Ruff, strict Mypy, default and full isolated PostgreSQL integration tests, frontend tests/build, codegen freshness, Docker build and bilingual consistency. Check existing mileage owner workflows, Expense reads and financial reporting.
- **Blind-review points**　Implementation matches D1–D6, documentation works for different clients, published tool counts match delivery, evidence distinguishes protocol automation from real client/manual checks, and local briefs are untracked.
- **DoD / reports**　Write `review-notes/M18-step4-impl.md` and `review-notes/M18-report.md` with commands, expected results, actual evidence, skips and the complete walkthrough below. Record acceptance after the author's walkthrough or explicitly delegated equivalent.

## Deployment self-tests and acceptance

Start the default dev Compose with `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d`. Use isolated test data and an owner-created test token. The milestone report provides the concrete MCP client setup and cleanup steps.

1. Create a token with `mileage:create` in Agent access. Verify localized capability wording and available transport types/default. Check an old token lacks permission.
2. Provide a date, one-way distance, return-trip choice and optional trip text. Inspect the complete preview, confirm, and check the exact returned web link, trip and linked Expense.
3. Select another enabled transport type and verify its applicable rate. Exercise a missing or ambiguous user description before preview.
4. Have the Agent present a route suggestion and source, correct its kilometres, and preview/confirm the corrected trip. Exercise manual fallback when search cannot supply a reliable distance. Record whether real search or controlled evidence was used.
5. Change the default transport, applicable rate or category after preview. Check rejection of the affected old preview, then create after a fresh preview and confirmation with a new attempt ID.
6. Retry an identical creation after a simulated lost response. Verify one trip, one Expense and the original replay result. Change the payload under the same ID and check the conflict.
7. Check the mileage list, linked Expense and reports for the backend-returned amount and existing zero-VAT treatment. Confirm owner-created mileage still works.
8. Revoke the token and verify denial on an existing MCP session and on replay. Record cross-company denial from the isolated two-company protocol tests.
