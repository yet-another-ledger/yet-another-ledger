## Dependencies and Existing Capabilities

- **M8/M8.5 Expense**: `ExpenseInput` requires date, category, PURCHASE-side VAT treatment, VAT rate, net and VAT amounts; it also carries deductible, payment source, business percentage and depreciation years. The Expense service validates dictionaries, applies backend-only `Decimal` rounding/snapshots and creates a non-draft Expense. Recurring Expense drafts are a separate workflow.
- **M8 receipt files**: `expense_attachment` stores metadata; `Storage`/`LocalStorage` retains originals. Existing validation accepts PNG, JPEG, WebP and PDF, checks declared MIME against magic bytes, and limits each file to `max_receipt_bytes` (10 MiB by default). Expense deletion already clears attachment metadata through FK cascade and disk files through the service.
- **M8 AI**: owner-configured OpenAI-compatible Chat Completions, receipt prompt, defensive `ExpenseAIPrefill` parsing and PDF rasterisation already exist. The current endpoint extracts from one Expense attachment without persisting the suggestion; M14 must preserve that endpoint while sharing its extraction core.
- **M10 reports**: Expense, P/L and VAT reports read Expense records. A pending inbox record must have no Expense row and therefore no accounting or report effect.
- **M15 dependency**: the future agent endpoint will call the same backend intake service. M14 adds no MCP server, agent credential, Telegram sender control or delivery idempotency key.

## Goal and Scope

**Goal**: accept original receipts before Expense creation, keep reviewable AI suggestions, and confirm one complete Expense with its original files only after the owner checks the accounting fields.

Included:

- A company-scoped inbox with pending and processed lists, detail/review view, and one expense-sized inbox item containing one to five original files (images and/or PDFs).
- Immediate durable upload and automatic whole-group AI extraction after creation or file changes; a manual retry action; failure and missing fields visible without blocking review.
- Manual confirmation using the existing `ExpenseInput` and Expense service rules, atomic attachment transfer, exactly-once Expense creation and a retained processed record linking to the Expense.
- Explicit discard of a pending item, including metadata and best-effort disk cleanup; no automatic expiration.
- EN/ZH frontend copy, contract generation, isolation/concurrency tests and a milestone-level walkthrough.

Excluded:

- M15's MCP/Telegram transport, agent authentication, sender allowlist and repeated-delivery deduplication.
- Automatic posting, AI-authored VAT treatment, supplier master-data creation, new currency/FX rules or a new report calculation.
- Backfilling existing Expenses or moving their existing attachments into the inbox.
- Automatic retention expiry, cross-item merge/split, and confirmation into an existing Expense. Multiple files must be grouped within one pending item before confirmation.

## Frozen Product and Architecture Decisions

- [x] **D1 · One item, one expense**: one inbox item represents one purchase and holds 1–5 files. Creation can upload several files; later uploads append to the same pending item. Confirming creates exactly one new PURCHASE Expense. MILEAGE and recurring drafts are ineligible.
- [x] **D2 · Original-byte retention**: use existing storage validation and per-file 10 MiB setting. Read no more than `max_receipt_bytes + 1` bytes per file before rejecting an oversize upload. File names are display metadata only; controlled UUIDs form storage keys. Confirmation transfers metadata ownership without copying or rewriting bytes.
- [x] **D3 · Separate pending entity**: pending items never create placeholder or draft Expenses. No Expense, P/L, VAT or Dashboard query reads inbox rows. Existing Expense data and report semantics stay untouched.
- [x] **D4 · Automatic advisory AI**: commit the upload first, then try extraction from the entire current file group using the configured provider. The web upload UI states before submission that enabled AI sends receipt content to that provider. PDFs keep the existing per-file page limit (`ai_pdf_max_pages`, default 3). Mixed groups retain each image's actual MIME in the model request; PDF pages are PNG. AI disabled, missing configuration, timeout, provider error or incomplete output leaves the item reviewable. The owner can retry explicitly.
- [x] **D5 · Suggestions are evidence, not authority**: persist only the parsed, validated `ExpenseAIPrefill` and a safe status/error code; never persist raw provider responses, credentials or image data in JSON. Show null/uncertain fields. VAT treatment is selected by the owner, never inferred as authoritative by the model.
- [x] **D6 · Whole-group freshness**: each file mutation increments `file_revision` and clears the previous suggestion/error. Extraction captures that revision and a run generation; only the latest run for the unchanged pending group may replace its suggestion. A stale run may finish but cannot overwrite a newer result or a confirmed item.
- [x] **D7 · Complete manual confirmation**: the request is the existing `ExpenseInput`, including every required dictionary and amount field. After extraction, the UI automatically places usable AI suggestions into editable inputs; the owner reviews or changes them and separately confirms. An extraction refresh must not overwrite fields the owner has already edited. The Expense service revalidates all values and performs all money calculations and snapshots. Confirmation creates `is_draft=false`.
- [x] **D8 · Exactly-once confirmation**: lock the pending item, create the Expense, transfer all files and mark the item confirmed in one transaction with no intermediate commit. A repeated or losing concurrent confirmation returns `409 ALREADY_CONFIRMED` with the existing `expense_id`; it never creates another Expense.
- [x] **D9 · Processed history**: confirmed items remain in a processed list with confirmation time and Expense link. `receipt_inbox.expense_id` uses `ON DELETE SET NULL`; if an Expense is later deleted through its existing path, the processed item remains and shows that its link is unavailable. Its original files follow the Expense deletion policy.
- [x] **D10 · Manual discard only**: a pending item remains until confirmation or explicit discard. Discard removes its metadata through FK/ORM cascade and deletes its files through the service. A confirmed item cannot be discarded or changed through inbox endpoints. Removing the final file is rejected; use item discard instead.
- [x] **D11 · Tenant/security boundary**: every route requires the existing MFA owner session and derives `company_id` from it. New inbox rows use PostgreSQL RLS with transaction-local company context; the attachment service enforces matching ownership during transfer and reads. Missing or cross-company IDs return `404` before storage or AI access.
- [x] **D12 · Recoverable storage failures**: validate a complete upload batch before persisting it; compensate newly written files if a later write or DB commit fails. For discard, remove DB-visible ownership first and then best-effort delete files, following the existing Expense deletion posture. Log cleanup failures without exposing private bytes; an unexpected process crash may leave an unreferenced disk file for administrator cleanup.

## Data Model and Migration

- Add `receipt_inbox`: UUID primary key, `company_id` FK/index, status (`PENDING`/`CONFIRMED`), nullable unique `expense_id` FK `ON DELETE SET NULL`, parsed suggestion JSONB, AI state (`NOT_RUN`/`RUNNING`/`READY`/`UNAVAILABLE`/`FAILED`), safe error code, `file_revision`, extraction generation, AI start/completion timestamps, creator and created/updated/confirmed timestamps. Add company RLS and the runtime-role grants used by current migrations.
- Make `expense_attachment.expense_id` nullable and add nullable `receipt_inbox_id` FK `ON DELETE CASCADE` plus index. A DB `CHECK` requires exactly one of those parent IDs. Existing rows retain their `expense_id`; no file or Expense backfill occurs. Keep `ExpenseAttachmentRead.expense_id` required for the existing Expense endpoints; use a separate `ReceiptInboxFileRead` without storage keys for pending files.
- Use the existing `receipts` storage namespace with a controlled company/item/file UUID key for new pending files. After confirmation the key remains opaque and unchanged even though the attachment belongs to an Expense. Existing content reads remain owner-guarded; generic Expense-attachment deletion and `/expenses/ai-extract` reject pending-owned attachments so inbox mutations cannot bypass versioning.
- Expense deletion uses its existing attachment cascade and disk cleanup. The processed inbox row remains through its `SET NULL` link. Downgrade refuses to run while any inbox row exists; after an administrator removes those rows, it restores the old attachment constraint and drops the new table. Upgrade preserves all legacy attachments.

## API Contract

All endpoints use owner/MFA authentication and server-derived company ownership. `ReceiptInboxRead` includes `id`, `status`, `files`, `ai_state`, nullable `ai_suggestion`, nullable safe `ai_error_code`, nullable `expense_id`, `created_at`, `updated_at` and nullable `confirmed_at`. `ReceiptInboxFileRead` includes ID, display filename, MIME, byte count and creation time; neither response includes a storage path or raw model response. `ReceiptInboxListResponse` is paginated newest-first with stable ID tie-breaking. Optional `language` defaults to `en`; the web client sends its active EN/ZH locale. List pagination defaults to `limit=50`, `offset=0`, with a maximum limit of 100.

| Endpoint | Request → response | Main guards |
| --- | --- | --- |
| `POST /api/v1/receipt-inbox` | multipart `files` (1–5), optional `language=en|zh` → `201 ReceiptInboxRead` | Validate the whole batch; persist originals before automatic AI attempt. AI failure is represented in the read model, not as upload failure. |
| `GET /api/v1/receipt-inbox` | `status=PENDING|CONFIRMED`, `limit`/`offset` → `200 ReceiptInboxListResponse` | Company-scoped, newest first. |
| `GET /api/v1/receipt-inbox/{id}` | → `200 ReceiptInboxRead` | Missing/cross-company → `404`. |
| `POST /api/v1/receipt-inbox/{id}/files` | multipart `files` (1–remaining capacity), optional `language` → `200 ReceiptInboxRead` | Pending only; increment revision and automatically re-extract whole group. |
| `DELETE /api/v1/receipt-inbox/{id}/files/{file_id}` | → `200 ReceiptInboxRead` | Pending only; at least one file must remain; increment revision and re-extract. |
| `POST /api/v1/receipt-inbox/{id}/extract` | `{language?: "en"|"zh"}` → `200 ReceiptInboxRead` | Pending only; explicit retry; AI failure still returns updated state. |
| `POST /api/v1/receipt-inbox/{id}/confirm` | `ExpenseInput` → `201 ReceiptInboxConfirmationRead {inbox, expense}` | One transaction; existing Expense validation; repeated/concurrent → `409 ALREADY_CONFIRMED` with `expense_id`. |
| `DELETE /api/v1/receipt-inbox/{id}` | → `204` | Pending only; remove metadata and clean files. |

File content uses existing `GET /api/v1/attachments/{attachment_id}/content`, subject to owner/company checks. `422` covers invalid files or an invalid `ExpenseInput`; `409` covers state/capacity conflicts, including removal of the final file. Missing/cross-company items and files return `404`. Public errors and logs contain no provider secrets, storage keys or receipt bytes.

Stable inbox conflict codes are `INBOX_NOT_PENDING`, `FILE_LIMIT_REACHED`, `LAST_FILE` and `ALREADY_CONFIRMED`. AI state `UNAVAILABLE` carries `AI_DISABLED` or `AI_NOT_CONFIGURED`; state `FAILED` carries `AI_TIMEOUT`, `AI_PROVIDER_ERROR` or `AI_INVALID_RESPONSE`. `READY` may still contain null fields, which remain manual-review work. Only `ALREADY_CONFIRMED` includes an `expense_id` in the error body.

## Transaction, AI and Failure Flow

1. Validate all uploaded parts and capacity, save controlled files, then commit inbox/attachment metadata. Compensate files written by the failed request if a later save or DB commit fails. A client timeout after commit can be recovered by listing the inbox.
2. Mark a pending item `RUNNING` for its current `file_revision` and extraction generation, then call the configured AI service outside a long-held row lock. Save parsed suggestions or a safe unavailable/failure state only if the item is still pending and both counters still match. Any pending `RUNNING` state left by process death is retryable; retry starts a new generation.
3. Lock the pending item for confirmation, validate the complete user `ExpenseInput` through the shared Expense service, create one Expense without an internal commit, transfer every attachment and mark the item confirmed before a single commit. An AI response arriving later cannot update the confirmed item. If Expense validation or transfer fails, the whole transaction rolls back and the original pending item/files remain.
4. Discard locks a pending item and removes its DB metadata through cascades; file deletion is best effort after the DB change. Existing Expense deletion keeps its current file-cleanup behaviour. No scheduled expiration job runs.
